# ADR-0003: Fail closed on deployed instances, with Cloudflare Access by default and an explicit opt-out

- **Status:** Accepted. The owner decided that an instance is private.
- **Date:** 2026-10-15
- **Issue:** #14

## Context

A deployed instance holds the owner's provider keys and spends the owner's credit on every `POST /api/decide/{provider}`, and `POST /api/warm/{provider}` (#9) would spend a connection in its name. The Deploy to Cloudflare button gives every fork a public `workers.dev` hostname, and the toolchain spike found that Wrangler also turns on Version URLs (`preview_urls`) when the config does not mention them, so each version gets a second public hostname ([`docs/spikes/worker-toolchain.md`](../spikes/worker-toolchain.md), step 4). Without a gate, anyone who finds the hostname can run up the bill before the owner has read a line of documentation.

The same `handle(request, env, deps)` serves the Worker on Cloudflare and the Node dev host inside `vp dev`, so the gate has to know which one is calling without trusting the request: a `Host` header or any other header is set by whoever sends the request.

## Decision

1. **A deployed instance refuses to call a provider until protection is configured.** `worker/protection.ts` runs in front of every non-GET route (decision 8), today the decide route and the warm route. With nothing configured it answers a JSON 503 that names the variables to set, and never reads the body.
2. **The recommended protection is Cloudflare Access in front of the Worker, with the Worker verifying the Access token itself.** The owner sets `ACCESS_TEAM_DOMAIN` (the team, as `team`, `team.cloudflareaccess.com`, or `https://team.cloudflareaccess.com`) and `ACCESS_AUD` (the application's audience tag). `worker/access.ts` then checks the `Cf-Access-Jwt-Assertion` header of every protected request: three base64url parts, `alg` exactly `RS256`, a `kid` found in the team's published keys, a valid RSASSA-PKCS1-v1_5/SHA-256 signature (Web Crypto), `iss` equal to the team domain, `aud` containing the tag, `exp` in the future, and `nbf` not in the future. A missing or failing token is a JSON 403 that names the problem category and never the token. Keys that cannot be fetched are a JSON 503, so an outage fails closed.
3. **The opt-out is one variable with one exact value.** `ALLOW_UNPROTECTED_INSTANCE` counts only when it equals `I accept the bill` (after trimming). Any other value leaves the instance unconfigured, with a message saying so. When Access and the opt-out are both set, Access wins.
4. **Local means the Node dev host, and nothing else.** `HandlerDeps.host` is `"node-dev"` from `server/vite-host.ts` and `"worker"` from `worker/index.ts`. The Node host runs only inside the Vite dev server on the developer's machine, so it skips the gate. workerd is treated as deployed even under `wrangler dev` or `vp preview`, because nothing inside workerd tells those apart from Cloudflare (`wrangler dev --remote` really is on Cloudflare), and because a "local" marker variable would be a second opt-out under a friendlier name. The cost is that a local run of the built Worker needs the same configuration a deployment does; `vp dev`, the documented way to develop, needs nothing.
5. **The keys are fetched for every verification and cached nowhere.** A cache that outlives a request would be the Worker's first mutable global. One extra Cloudflare-to-Cloudflare fetch per protected request is small next to the provider call (0.4 to 1.3 s). If it ever matters, the cache belongs in `worker/index.ts`, created once per isolate and passed in through `HandlerDeps`, where a test can replace it.
6. **`GET /api/providers` reports the state** as `protection`: `local`, `opted_out`, `unconfigured` (with a detail naming the missing variables), or `access` with `validated` saying whether that very request's token passed. The list itself needs no token, because it is the public catalog filtered by which keys are set, and the browser needs the state to show the notice. The UI fills `#protection-notice` for `unconfigured`, `opted_out`, and `access` with `validated: false`.
7. **`wrangler.jsonc` sets `workers_dev: true` and `preview_urls: false`.** The `workers.dev` hostname stays, because a fork deployed with the button has no other. Version URLs go, so no version gets a second public hostname. The gate lives in the Worker's code rather than in the hostname, so for a version built from this change a hostname added later (a custom domain, or Version URLs turned back on) is covered too. Versions from before this change carry no gate: rolling back to one, or turning Version URLs on while one exists, exposes an ungated Worker that may still hold the provider keys, because secrets survive deploys. The guide says not to do either. Verified on Cloudflare's pages: the defaults of `workers_dev` and `preview_urls`, that disabling `workers_dev` leaves Version URLs alone, and the Version URL hostname shape. Not verified, and assumed unsafe: whether an older version becomes reachable by a Version URL once they are turned on, and whether a rollback re-exposes an old version with the current secrets.
8. **Every non-GET route is gated by default.** The dispatcher in `worker/handler.ts` sends any request whose method is not GET or HEAD through the gate before its route runs, unless the route is listed in `UNGATED_ROUTES`, which is empty and must carry a comment for every entry. So the warm route of #9 is gated without anyone wrapping it: on an unconfigured Worker it answers the gate's 503 before its own 501, and with the opt-out it reaches that 501, because a Worker has no connection pool to warm.
9. **Secrets rather than `vars` for the three variables.** The guide recommends `wrangler secret put` for them even though none is secret, because a `wrangler deploy` overwrites dashboard-set `vars` unless `keep_vars` is set, while secrets survive every deploy (confirmed in the spike, step 5).

Two things the pages do not state, left for the live check in [`scenarios/14-fail-closed.feature`](../../scenarios/14-fail-closed.feature): that the `Cf-Access-Jwt-Assertion` header reaches the Worker when Access is enabled at the Worker level rather than on a hostname (the Workers page documents `ctx.access` for that case and does not mention the header), and where the dashboard shows the team domain (the validating page gives its shape, `<team>.cloudflareaccess.com`).

**Live check, 2026-10-19,** on the owner's instance (Worker-level Access, All traffic, a policy that allows one email address):

- **The header reaches the Worker.** After signing in through Access, `GET /api/providers` reported `"protection": { "mode": "access", "validated": true }`, so the Worker received the token in `Cf-Access-Jwt-Assertion` and verified it. A run then succeeded on all three providers.
- **The dashboard shows the team domain on the Worker's own Access tab.** Under "Application values" it lists the AUD tag and a JWKS URL, `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`, which contains the team domain.
- **Access stops unsigned requests first.** Without a session, `/`, `GET /api/providers` and `POST /api/decide/typesafe` all answered Access's 302 to its login page. That was true even with a forged `Cf-Access-Jwt-Assertion` header, so the Worker's own 403 is a second line that a request through the `workers.dev` hostname never reaches.
- **Not checked:** the scenario's `wrangler tail` step, which looks for the key or the token in logs.

## Consequences

- A fork deployed with the button answers every run with the 503 and shows the notice until its owner acts. That is the point.
- The owner's instance runs behind Access. Each protected request costs one extra fetch of the team's keys.
- `GET /api/providers` grows a required `protection` field; the browser schema requires it, so server and client ship together.
- `wrangler dev` on the built Worker needs `ACCESS_*` or the opt-out, passed with `--var KEY:VALUE`; `vp preview` has no way to receive them, because `.env.schema` deliberately does not declare them (#18); `vp dev` needs nothing, and counts as local whatever address it listens on.
- The key fetch uses `redirect: "manual"`, because workerd implements only `"follow"` and `"manual"` and throws on `"error"`; a 3xx from the certs endpoint is refused by status, its body cancelled unread.
- The verification has no clock leeway and no JWT library. Both are deliberate: Access and the Worker run on Cloudflare's clocks, and Web Crypto covers RS256.
- Turnstile (#65), rate limiting (#66), and billing alerts remain follow-ups for owners who want a public instance.
